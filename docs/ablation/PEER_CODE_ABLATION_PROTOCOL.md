# SDK間生成コードの有無だけを切り分ける

主仮説：最新の他SDK生成コードを見せると、評価情報だけを見せる場合より公式合格数が上がる。
台帳の診断共有を外したrestart構成で、同じモデル・同じ初回126件・最大5修正を使う。

- shared：元構成と入力を変えず、最新の他SDK生成コードを渡す。
- masked：同じ履歴から作った入力の他SDK code欄だけを非表示マーカーに置換する。
- 両方とも他SDKの問題文・合否・観測出力・エラーを渡す。自身の診断は保持、他SDKの診断は非共有。
- 元と同じ条件で、自身の過去コード・診断の停滞時マスキングを行う。
- 各修正1モデル呼出し・1コード・1公式評価。合格後停止。最大6提出/SDK。
- 初回のモデル生成・評価は共通の保存結果を使用。その後は4条件とも新しく生成する。
- 全126ケースを各条件2回ずつ。途中の合格数によらず4系列すべて完了する。
- 以前の108件の系列は今回の主比較へ混ぜない。

主指標：2回を平均した共有あり−なしの合格数差。各回の差も必ず報告する。
42問題について3SDKと2回を平均した対応差を20,000回bootstrap（seed20260916）。
両方の回で差が正、かつ95%区間の下限が0を超える場合のみ、この設定で一貫した正の効果を支持したと扱う。
そうでない場合は正の点推定、証拠不十分、逆方向を区別し、望む結論に合わせない。
同点で区間[0,0]でも一般的な無効性や同等性を証明したとは扱わない。

対照にもコード利用の元の指示文を残し、コード欄に非表示であることを明記する。
エラーにソース断片が含まれ得るため、「完全にあらゆるコード情報を除く」実験ではない。
同じ履歴に適用する加工はコード欄だけだが、生成が分岐した後の履歴・観測値は条件ごとに変わる。
このベンチマークは開発にも使用した。トークン数、入力長、LLM生成乱数は一致させていない。

実行前のソースhash・設定・起動順・回復規則は `results/ablation/peer_code_ablation_registry.json`。
途中の生ログは runs/peer_code_{shared,masked}_r{1,2}/。
完了後に `.venv/bin/python -m qagent.peer_code_report` で監査・集計する。
